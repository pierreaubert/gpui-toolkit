# gpui-toolkit: performance, memory, power and correctness audit

Date: 2026-10-18

Audited revision: `f556d489c6b78ff3c41d1b858ad44f76b59d2916`

Dependency fork inspected: `sotf-3rdparties` at `d476ae9bc3165145d4a8e43b6bafbef11b196a04`

## 1. Assessment

The largest immediate opportunities are to **stop repeating work, bound retained memory in bytes, and remove synchronous GPU readback from interactive paths**. Moving the existing work to CUDA or MLX before fixing those boundaries would preserve substantial avoidable cost.

There are useful foundations: shared mesh storage, retained builder output, allocation-contract tests, a retained GPU scene, a prepared GPU flow implementation, and direct GPU drawing elsewhere in d3rs. These should be extended and connected. The ordinary scene3d GPUI element currently bypasses much of that advantage: each paint invokes the software rasterizer, including geometry preparation.

The correctness problems are material for scientific visualization. A Metal reproduction showed a clipped cube disappearing after translation, although its shape and relative clipping plane were unchanged. Other reproductions found ignored validity masks, inconsistent velocity/diagnostic fields, ignored wireframe rendering, and incorrect transparency classification. Passing existing tests does not establish equivalent rendering or numerical semantics across backends.

Testing has meaningful breadth, but its strongest evidence is for local functional behavior and selected allocation contracts. The performance CI has a concrete collection/comparison failure mode that permits a green result without a useful comparison. Mobile compile jobs and desktop tests do not establish mobile memory, thermal, power, IME or lifecycle behavior.

Recommended order:

1. Repair performance evidence collection and add regression tests for the reproduced correctness failures.
2. Make scene preparation persistent; connect scene3d to the host GPU device and command stream.
3. Establish byte budgets, streaming boundaries and demand-driven frame scheduling.
4. Improve the existing portable GPU and CPU pipelines.
5. Evaluate incremental use of the Taffy already present in GPUI.
6. Add optional CUDA and MLX implementations only where end-to-end measurements justify them.

## 2. Scope and evidence

This audit used implementation files, manifests, shaders, tests, benchmarks and CI scripts. Repository prose was not treated as evidence that a feature works. External primary sources were consulted for the requested Taffy evaluation and the CUDA/MLX integration plan.

This is a risk-focused audit across the platform, not a line-by-line certification of every component. CLI, theme tooling, every chart type, and all native platform services were not exhaustively executed. No phone energy trace, CUDA benchmark, MLX benchmark, browser execution or full workspace test run was performed. Findings distinguish reproduced behavior from source-established behavior and runtime hypotheses.

The TokenSave graph lagged the checkout by one commit. It was used for navigation; findings were checked against current source reads. Line references below refer to the audited checkout. The worktree was clean before this report.

Evidence labels:

- **R — reproduced:** a bounded local experiment demonstrated the behavior.
- **S — source:** the relevant implementation establishes the behavior; no separate runtime reproduction was performed.
- **H — hypothesis:** a credible integration risk that needs a platform/runtime test.

Priority **P1** means address before relying on the affected path for production correctness, large datasets or mobile efficiency. **P2** means planned optimization/hardening. These are engineering priorities, not vulnerability severity scores.

## 3. Measurements and executed checks

### 3.1 Scene preparation is allocation-heavy before rasterization matters

Host: Apple M4 Pro, 14 CPU cores, 64 GiB RAM, macOS 27.0.1, Rust 1.99.0. A separate release harness linked the local mesh, scene3d, transformation, pretext and profiler crates. `AllocProbe` instrumented allocations. Each operation had one warmup followed by five measurements; the table shows the median within each run. Results were consumed with `black_box`; destruction of the returned result was outside the measured interval.

The datasets were structured grids spanning `[-1, 1]³`, with one constant point scalar. `n³` is the point count, not the cell count. Preparation used a 100,000-triangle chunk cap; rendering used a 128×128 image. The small image deliberately exposes geometry/CPU overhead.

| Grid | Operation | Run A median ms | Run B median ms | Allocation calls per operation | Cumulative allocated bytes per operation |
|---|---|---:|---:|---:|---:|
| 16³ points / 3,375 hexes | Prepare | 1.439 | 1.750 | 40,551 | 2,451,152 |
| 16³ | Software render | 2.149 | 2.498 | 45,966 | 3,021,800 |
| 32³ points / 29,791 hexes | Prepare | 12.529 | 20.898 | 357,552 | 19,504,120 |
| 32³ | Software render | 14.753 | 98.229 | 380,633 | 21,463,312 |
| 48³ points / 103,823 hexes | Prepare | 62.484 | 316.053 | 1,245,941 | 73,642,256 |
| 48³ | Software render | 57.104 | 280.614 | 1,298,975 | 77,760,040 |

**The allocation counts and bytes reproduced; the wall times were noisy.** These are two observed run medians, not confidence intervals or representative device frame budgets. The shared host was not isolated. In particular, preparation being slower than preparation-plus-render in some samples is timing noise, not an algorithmic conclusion.

Run B's complete bounded probe used 1.74 s user CPU, 0.04 s system CPU and 4.43 s elapsed time. `/usr/bin/time -lp` reported 85,884,928 bytes maximum RSS, about 81.9 MiB, for the whole process. This is neither per-operation peak memory nor GPU memory. Allocated-byte totals above are allocation traffic, not simultaneously live memory. The allocator instrumentation and the scratch harness's separate Cargo resolution also preclude treating these as a production application benchmark.

The robust result is the scale of avoidable work: a 48³ grid with only 26,508 external surface triangles causes roughly **1.3 million allocations for one tiny software frame**. That is a poor starting point for mobile power efficiency even before increasing image resolution.

## 4. Correctness findings

### C1 — P1 / R: GPU clipping uses rebased vertices with world-space planes

Sources: [prepare.rs](crates/gpui-scene3d/src/prepare.rs), lines 66–138; [gpu_render.rs](crates/gpui-scene3d/src/gpu_render.rs), lines 393–435; [shaders.rs](crates/gpui-scene3d/src/shaders.rs), lines 51–65; [scene.rs](crates/gpui-scene3d/src/scene.rs), lines 24–42.

Preparation stores positions relative to the dataset origin. The GPU matrix restores the translation for projection, but the shader assigns the un-restored position to `world_position`. Plane origins are uploaded in the original world coordinates. The fragment half-space test therefore compares different coordinate systems.

The translated-cube reproduction in §3.2 makes this visible without relying on image similarity thresholds. Geometry around x=1000 becomes local x≈±1, which the shader then compares against a plane origin of x=1000.

**Change:** define one camera/actor-relative coordinate convention and convert both vertices and planes before the f64-to-f32 boundary. Avoid restoring a large world origin in f32 merely to subtract it again. Apply the same convention to clipping, picking, lighting and volume rays.

**Regression:** translation-invariance tests at zero, moderate and large origins; non-axis-aligned planes; multiple actors with different origins; CPU/GPU half-space agreement. Test geometric coverage and numerical tolerances separately from color interpolation.

### C2 — P1 / R: prepared flow returns a dataset with mixed time steps

Source: [gpu.rs](crates/gpui-dataset-transformation/src/gpu.rs), lines 641–649, 849–863 and 918–932.

`PreparedFlow::diagnostics(Some(new_velocities))` updates the GPU velocity buffer and computes new diagnostics, then constructs the returned dataset by cloning `self.base` and replacing only the diagnostic fields. The original velocity field survives. Zero-velocity input produces zero Q alongside nonzero velocity vectors.

This can silently corrupt a downstream calculation, glyph view or export that assumes all fields in a `DataSet` describe the same sample. A subsequent `diagnostics(None)` also operates on the retained updated GPU buffer while the base field remains old.

**Change:** retain the field identity and current velocity revision, and return a consistent dataset; alternatively return an explicitly revisioned diagnostics result rather than pretending to return a coherent replacement dataset. Preserve validity information. Keep shared geometry storage.

**Regression:** zero/nonzero updates, two successive updates, `None` after an update, and downstream CPU recomputation from the returned velocity field. Compare all returned fields, not just Q.

### C3 — P1 / R+S: field validity masks are not consistently honored

Sources: [field.rs](crates/gpui-mesh/src/field.rs), lines 84–86; [threshold.rs](crates/gpui-dataset-transformation/src/threshold.rs), lines 35–55; [scene.rs](crates/gpui-scene3d/src/scene.rs), lines 198–201; [prepare.rs](crates/gpui-scene3d/src/prepare.rs), lines 79–103.

Thresholding checks the stored values but not the field's `valid` mask. This reproduces with a dataset that passes `validate()`. Scene scalar resolution similarly discards validity and passes only values into preparation. Finite placeholder values in invalid entries can therefore enter a selection or appear as valid measurements.

**Change:** define explicit validity semantics for each operation: threshold All/Any, cell-to-point averaging, interpolation, diagnostics and rendering. Carry a mask or deliberately convert invalid samples to a documented missing-value representation at the boundary. Do not average invalid values into valid ones. Some interpolation code already propagates masks; use a common contract rather than different local rules.

**Regression:** all-invalid and partially invalid point/cell fields, finite invalid placeholders, NaNs, empty selections and CPU/GPU agreement. This is scientific correctness, not merely display styling.

### C4 — P1 / R+S: scene backends implement different material and geometry semantics

Sources: [scene.rs](crates/gpui-scene3d/src/scene.rs), lines 185–186; [raster.rs](crates/gpui-scene3d/src/raster.rs), lines 206–289 and 293 onward; [prepare.rs](crates/gpui-scene3d/src/prepare.rs), lines 115–138; [gpu_render.rs](crates/gpui-scene3d/src/gpu_render.rs), lines 240–271 and the render loop; [shaders.rs](crates/gpui-scene3d/src/shaders.rs).

Specific discrepancies:

- Transparency classification ignores transfer-function alpha. The alpha-0.25 reproduction enters the opaque path. CPU blending and GPU depth-write/pass selection consequently do not follow the material's actual opacity.
- Wireframe preparation builds edges, but neither the software triangle path nor GPU triangle upload/draw consumes those edges. This both wastes work and leaves the requested overlay absent.
- Software triangles use a triangle-average scalar and one vertex normal; GPU shaders interpolate scalar/normal values. A smoothly varying field is rendered differently. A CPU image is not currently a pixel-equivalent GPU oracle.
- GPU plane uniforms cap the list at six, whereas software clipping processes the supplied list. Excess planes need an explicit supported-limit error or equivalent behavior.
- Software line rendering does not use the actor's clipping-plane path. GPU scene rendering does not provide the equivalent line/point path used by all CPU scene content.
- GPU transparency is ordered by actor center, not per intersecting surface. Software per-actor triangle sorting is also insufficient to resolve arbitrary intersections between actors. Treat sorted transparency as an approximation until a defined compositing method is implemented.

**Change:** create a backend capability/semantics contract. Implement transfer-alpha-aware pass selection, line/wireframe paths and consistent scalar interpolation. Return explicit unsupported-feature errors where parity is not yet implemented. For interactive translucent scientific surfaces, evaluate weighted blended order-independent transparency; reserve more exact methods for use cases that require them. State the approximation and test it.

**Regression:** two overlapping translucent actors, alpha gradients, cell/point scalars, clipping lines and wireframe, more than six planes, and gradients on one triangle. Test invariants and bounded differences; do not hide semantic mismatches under a loose screenshot tolerance.

### C5 — P1 / R+S: dimensions and allocation sizes are insufficiently checked

Sources: [raster.rs](crates/gpui-scene3d/src/raster.rs), lines 66–83; [volume.rs](crates/gpui-scene3d/src/volume.rs), around line 258; [gpu_render.rs](crates/gpui-scene3d/src/gpu_render.rs), target/readback allocation around lines 357 and 508–512; [vtu.rs](crates/gpui-dataset-transformation/src/vtu.rs), lines 93–129.

Image arithmetic such as `width * height * 4` is performed before a sufficiently wide checked size calculation. Release overflow can produce a dimensioned frame with an invalid backing length; other cases can panic or request excessive memory. Safe indexing does not make this memory corruption, but it is a public API correctness and availability problem.

The compressed VTU path also trusts header-derived lengths too early: integer conversion/arithmetic and capacity allocation precede complete validation, and decompression uses unbounded `read_to_end` before final size checking. A small compressed input can demand excessive memory.

**Change:** use checked size arithmetic, limits from the actual GPU device, and a host-supplied byte budget before allocating. Validate row padding, aggregate staging buffers, decompressed output, cell counts and index counts. Return structured errors; use fallible reservations where practical. A triangle cap alone is not a process-memory budget.

**Regression:** arithmetic-only boundary cases, malformed/truncated compressed headers, bounded expansion, 32-bit/wasm size constraints and allocation-failure behavior. Avoid tests that actually attempt multi-gigabyte allocations.

### C6 — P1 / S+H: FFI and thread ownership need stronger enforceable boundaries

Sources: [Windows foreign_parent.rs](crates/gpui-win-foreign/src/foreign_parent.rs), lines 313–352; [Android window.rs](crates/gpui-android/src/android/window.rs), lines 486, 514, 1525–1531, 1702, 2092–2151; [registry.rs](crates/gpui-foreign-parent/src/registry.rs), registration/access functions; [Linux editor.rs](crates/gpui-linux-foreign/src/editor.rs), thread checking and unregister.

There are two different concerns:

1. **Source-established Rust API safety mismatch:** public safe `extern "C"` functions such as `gpui_win_destroy` accept an arbitrary raw pointer and reconstruct a `Box` from it. Safe Rust callers can violate the required validity/ownership precondition. Mark the Rust entry points `unsafe extern "C"` with explicit contracts, or use checked opaque handles. The C ABI need not change. Review analogous exports together.
2. **Thread/lifetime proof gap:** Android transmutes non-`Send` callbacks into `Send` callback types and marks raw platform state as thread-safe. A comment that callbacks are invoked on the main thread does not by itself constrain moving/dropping their captures. Shared foreign-parent registries also depend on external pointer type, thread and lifetime discipline; release-only absence of `debug_assert!` checks is not enforcement. Reentrant teardown is particularly important to test.

No invalid-pointer execution or Android race was attempted. The second category is a source-identified risk, not a demonstrated race in the normal event loop. Existing unsafe registration contracts do impose obligations on callers; their existence should not be confused with complete enforcement by the safe access API.

**Change:** keep non-`Send` ownership in a UI-thread-local owner; send typed commands/IDs across threads. Bind registry entries to their concrete type and lifetime. Use generation-checked handles and an explicit closing/in-callback state; defer destruction until active callbacks complete. Add release-mode thread checks at host entry points and prevent unwinding across FFI.

**Regression:** repeated create/destroy, callback-triggered destruction, queued work after close, resize during teardown, cross-thread rejection and stale handles. Extend Miri to platform-neutral ownership code and use native sanitizers for the platform boundaries.

### C7 — P2 / S: text editing is scalar-based; raw measurement cache identity is implicit

Sources: [edit_state.rs](crates/gpui-ui-kit/src/input/edit_state.rs), lines 133–148 and movement/deletion methods; [measurement.rs](crates/gpui-pretext/src/measurement.rs), lines 35–53 and 275–305.

Input cursor movement counts Rust `char`s and increments/decrements scalar positions. That can place a caret inside an extended grapheme such as a combining sequence or emoji joined with ZWJ. Repeated character-index-to-byte conversion scans the string, adding cost for long inputs. Native UTF-16 offsets, grapheme navigation and bidirectional visual movement need distinct conversions and tests.

The raw pretext `MeasureCache` is keyed by text alone, although it accepts a measurement provider on each call. Reusing it across providers returns the first provider's metrics, as reproduced. This can be a caller-owned per-font cache, but its API does not enforce that scope. The builder's retained measurement machinery already has identity/revision concepts; do not remove that protection or assume every cache lacks it.

**Change:** enforce measurement identity at cache construction or include an explicit semantic generation; invalidate for font, scale, locale and shaping changes. Use grapheme/cluster boundaries for editing, maintain efficient index maps, and test native composition/caret behavior independently of line wrapping.

## 5. Performance and memory findings

### P1 — P1 / R+S: scene3d reconstructs geometry during ordinary GPUI painting

Sources: [element.rs](crates/gpui-scene3d/src/element.rs), lines 115–133; [raster.rs](crates/gpui-scene3d/src/raster.rs), lines 66–130, 162 onward and 206–289; [prepare.rs](crates/gpui-scene3d/src/prepare.rs), lines 66–138; [chunk.rs](crates/gpui-mesh/src/chunk.rs), lines 63–160.

The ordinary element calls `render()` from `paint()`, then constructs a new `RenderImage`. Each render allocates RGBA/depth storage and calls `prepare_chunks` per actor. Preparation rescans bounds, copies point scalars or constructs cell-to-point arrays, extracts surfaces, computes normals and builds chunks. Software clipping/projecting also creates small vectors per triangle, including a polygon vector when there are no planes.

Boundary extraction uses heap-backed face vectors as keys and values; internal faces remain represented in the hash map. All boundary triangles are materialized before all chunks are collected. The per-chunk triangle cap therefore bounds a chunk, not total preparation memory. Hash iteration also makes emitted order unstable; canonical topology is preferable for reproducible chunks, caching and transparent ordering.

The allocation measurements in §3.1 follow directly from this structure. Dataset cloning itself is not the main issue: positions and fields use shared storage. The costly work is rebuilding derived representations.

**Change:** retain topology, bounds, surface indices, normals, prepared chunks and GPU buffers by explicit revisions. Camera changes should touch camera uniforms; scalar changes should update only affected scalar buffers. For software fallback, retain geometry and reuse frame/scratch storage. Replace tiny face-vector keys with fixed-size canonical keys plus arity; avoid whole-mesh intermediate duplication and use byte-bounded staging. Calculate shared vertex normals before partitioning when continuity is required.

The element also renders using logical bounds without applying the window's device scale. Specify physical target dimensions and test high-DPI behavior; resolution reduction for power should be an explicit quality policy, not accidental undersampling.

**Acceptance:** a warmed camera-only repaint performs no topology extraction or geometry upload, and no mesh-size-proportional CPU allocation. Measure the entire presentation path, not only a standalone render call.

### P2 — P1 / S: GPU work is fragmented and often read back synchronously

Sources: [gpu_render.rs](crates/gpui-scene3d/src/gpu_render.rs), renderer construction, upload/render and `read_rgba`; [transformation gpu.rs](crates/gpui-dataset-transformation/src/gpu.rs), lines 127–185, 193–405, 445–469 and 615–944; [d3rs surface3_drenderer.rs](crates/gpui-d3rs/src/gpu3d/renderer/surface3_drenderer.rs), lines 725–814.

There are important distinctions:

- `GpuRenderer` already retains uploaded geometry and supports camera changes through uniforms. Preserve this design. Its standalone device/queue, target and submission API are not the same as a host-integrated GPUI draw path; the standard element still uses software rendering.
- `GpuFlow::point_jacobians` tetrahedralizes, uploads and allocates buffers per call, reads per-tetrahedron Jacobians/volumes back and reduces on the CPU.
- **`PreparedFlow` already improves this:** it retains geometry and point-to-tetrahedron adjacency, and computes point diagnostics on the GPU. It is not appropriate to propose adding this from scratch. However, every diagnostics call still creates three readback buffers, performs blocking maps/waits and reconstructs CPU f64 result arrays. It cannot keep a produced field on-device through rendering.
- The prepared kernel recalculates tetrahedron geometry for each adjacent point. With fixed geometry, a per-tetrahedron inverse/volume cache or a measured two-pass implementation can avoid that repetition. Compare its storage/bandwidth cost against arithmetic saved.
- The d3rs `Surface3DRenderer` path copies the image to staging, blocks on GPU completion and creates CPU pixels. Other d3rs/custom-draw paths already demonstrate a more direct integration; this is not a claim that all d3rs rendering reads back.

Both flow implementations dispatch a one-dimensional workgroup count without a complete large-input partition/capability plan. Buffer-size limits and dispatch limits must be checked before creating buffers. For illustration, a 65,535-workgroup x limit with 64 threads allows about 4.19 million invocations in one dispatch; actual requested device limits determine the valid bound. The older per-tet path also stores 36 bytes of Jacobian plus 4 bytes of volume per tet, then duplicates those outputs for readback.

**Change:** inject the existing host GPU context; encode compute and rendering into coordinated submissions; expose revisioned resident result buffers; read back only when the consumer actually needs CPU data. Reuse a bounded staging ring for exports/picking. Partition large work by device limits. Make asynchronous initialization/readback the portable API, especially for web; keep blocking wrappers explicitly offline/native.

High-performance adapter preference and `MemoryHints::Performance` are currently chosen locally. Let the host choose a power/memory policy instead of each subsystem creating its own high-performance context.

### P3 — P1/P2 / S: cache bounds are not consistently memory bounds

| Cache/path | Source-established issue | Recommended change |
|---|---|---|
| Axis tick labels | [misc.rs](crates/gpui-d3rs/src/axis/render/misc.rs), lines 5–26: thread-local map of floating-point values/formatter identities has no eviction | Byte/entry LRU or chart-owned lifetime, with locale/format revision |
| Mesh software image fallback | [element.rs](crates/gpui-d3rs/src/mesh/gpu/element.rs), lines 15–88: 32-entry cap and whole-cache clearing; no pixel-byte budget | Byte-budgeted LRU, obsolete-revision removal and size-aware admission |
| Pretext measurements | [measurement.rs](crates/gpui-pretext/src/measurement.rs), lines 188–305: linear `VecDeque` search on each hit; byte accounting excludes grapheme arrays/container overhead; last oversized entry retained | O(1) or measured approximate recency; account for payload allocations; bypass cache for oversized entries |
| Wasm gpu2d initialization failure | [device.rs](crates/gpui-d3rs/src/gpu2d/device.rs), line 71: each access in failed state clones and leaks an error string | Store owned/shared error once; no allocation on repeated failure |

A 32-entry image cache can still retain roughly 512 MiB if each CPU image is 2048×2048 RGBA8, before any GPU copies. This is a capacity example, not a measured cache occupancy. Pretext's existing entry/text budget is useful, but it should not be advertised or used as a hard cap on total cache memory.

**Acceptance:** memory plateaus under long-running zoom/stream/resize churn; an oversized item cannot consume the cache's entire mobile budget; repeated failed GPU initialization has constant retained memory. Publish CPU and GPU cache byte counters, high-water marks and trim hooks.

### P4 — P2 / S: table virtualization does not remove full-data ownership cost

Sources: [table.rs](crates/gpui-ui-kit/src/table.rs), constructor, `virtual_window` and body construction; [table benchmark](crates/gpui-ui-kit/benches/table.rs), lines 79–98.

Visible-window construction exists, which is valuable. The default is nevertheless the full row range, and the API takes an owned `Vec<T>`. A caller that clones all rows on each render can pay O(total rows) even when only visible rows are built; the benchmark includes this pattern. Sorting is owned by callers, so this is not a claim that `Table` itself sorts all rows each frame.

**Change:** support shared immutable rows or a row provider, stable row IDs, viewport-driven virtualization and incremental cell updates. Keep overscan small and bounded. Test selection/focus/accessibility as rows enter and leave the window.

**Acceptance:** warmed scroll/camera-independent updates scale with visible rows, not total rows; include the caller's data preparation in the benchmark. Retain the useful existing headless build/layout/paint benchmark rather than replacing it with a constructor microbenchmark.

### P5 — P1/P2 / S: volume and movie paths need bounded working sets

Sources: [volume.rs](crates/gpui-scene3d/src/volume.rs), tetrahedron sampling and lines 202–310; [animate.rs](crates/gpui-scene3d/src/animate.rs), frame generation; [movie.rs](crates/gpui-scene3d/src/movie.rs), lines 63–70 and 85–145.

The retained `VolumeRenderer` is a useful start, but it copies the scalar array and uses a grid of per-bin vectors. At a 64³ grid, empty vector headers alone are approximately 6 MiB on a 64-bit host, before tetrahedron references. Sampling repeatedly recomputes barycentric geometry. The current raycaster is a CPU pixel/ray loop; adding more threads without a working-set and cancellation policy can increase mobile power.

**Change:** cache tetrahedral transforms and bounds, pack bins as CSR or use a measured BVH/brick structure, skip empty space, and allow a progressive resolution/step budget. Make volume opacity integration explicitly step-length-aware and test convergence. Share immutable scalar storage where possible and replace only the field revision.

Movie APIs retain raw frames and, for PNG sequences, all encoded frames as well. One 1920×1080 RGBA8 frame is 7.91 MiB; 300 raw frames are about 2.32 GiB. Separately, software RGBA plus f32 depth requires at least 15.82 MiB at 1080p or 63.28 MiB at 4K, before scene geometry and presentation copies.

`mux_mp4` feeds all PNG input before `wait_with_output` drains stdout/stderr. This creates a pipe-backpressure deadlock risk for sufficiently large output: the encoder may wait for its output pipe while the parent waits to write input. This was source-reviewed, not reproduced with a large movie.

**Change:** provide iterator/stream-to-writer APIs, a small frame queue, concurrent encoder-output draining, cancellation and cleanup. Reuse buffers. Keep the in-memory convenience API for deliberately small exports with explicit limits. Native hardware encoding can be evaluated after streaming is correct.

### P6 — P1 / S: the Python text-line limit is checked after allocation

Source: [python.rs](crates/gpui-python-runtime/bin/showcase/python.rs), lines 815–854.

`read_until` accumulates the complete control line before checking its size. A large or unterminated line can allocate far beyond the nominal limit, and clearing the vector retains that capacity. The binary-frame path does check lengths before resizing; the text path should provide equivalent protection.

**Change:** enforce the limit while reading, discard/reject excess bytes with bounded storage, and bound total queued bytes as well as message count. Retain the existing bounded-queue/event-driven structure. Test oversized lines in small chunks and without a newline, plus recovery behavior.

## 6. Power and platform behavior

Power should be measured as energy per useful operation and idle wakeups, alongside frame latency. Lower CPU time is a strong objective, but a GPU offload that forces frequent synchronization, increases memory traffic or holds a discrete GPU awake can still lose overall.

| Platform/path | Evidence and concern | Action and validation |
|---|---|---|
| iOS/tvOS showcase frame loop | [iOS AppDelegate.swift](crates/gpui-showcase/ios/ShowcaseApp/AppDelegate.swift), lines 7–23, and [tvOS equivalent](crates/gpui-showcase/tvos/ShowcaseTV/AppDelegate.swift): repeating display link without an application dirty/animation pause policy in this shell | Schedule for damage/animation, pause on inactivity, coalesce resize/input and select refresh rate deliberately. An idle callback is not proof of an idle GPU redraw; measure both. |

Proposed common policy: a host-owned frame scheduler receives damage, animation deadline, visibility, interaction, thermal state and memory pressure. It chooses whether to schedule, target cadence, render resolution and optional-work budget. Caches receive a shared byte budget and trim signal. Background or superseded computations should be cancelled or their work stopped at chunk boundaries.

Measure real devices for: 60 seconds of static idle; continuous scroll/orbit; a streaming field update; a 20-minute thermal soak; background/foreground; memory pressure; and repeated window/editor creation. Record frame callbacks, actual draws, CPU time, allocations, peak resident memory, GPU memory, dropped frames and energy. Keep screen brightness, refresh rate and workload duration controlled. Desktop microseconds cannot establish phone battery behavior.

## 7. Test quality and the performance gate

### Q1 — P1 / R+S: performance CI can report success without matched data

Sources: [ci.yml](.github/workflows/ci.yml), lines 755–808; [qa_perf_baseline.py](scripts/qa_perf_baseline.py), lines 37–38, discovery/build/output functions; [qa_perf_check.py](scripts/qa_perf_check.py), lines 66–85 and 357–417.

The base-revision CI step sets `CARGO_TARGET_DIR` to a separate directory. Cargo writes benchmark results there, while the collector hardcodes `ROOT / "target" / "criterion"`. With the audited collector on the base revision, a clean base worktree therefore has no results at the inspected path. Empty collection can still be serialized successfully.

The comparison accepts empty record lists. It does not require a nonempty matched set; missing benchmarks are warnings, and candidate-only benchmarks are treated as new. An empty base can make all current benchmarks appear new. A direct two-empty-file invocation returned exit code 0. This is a configuration/code failure mode; it is not a claim that every historical CI run used an identical base script.

**Required repair:**

1. Resolve the actual Cargo target directory, including `CARGO_TARGET_DIR` and configuration overrides, or pass the Criterion directory explicitly.
2. Fail collection if any required benchmark family emits no fresh samples.
3. Fail comparison on empty inputs, zero required matches, disappeared required cases or incompatible configuration. Allow intentional benchmark changes through an explicit manifest/update path.
4. Record source revision, feature set, toolchain, device/backend, target directory and run ID. Verify sample freshness; cached Criterion files must not masquerade as the current run.
5. Add end-to-end fixture tests with separate base/candidate target directories. Unit tests of parsing/environment comparison alone did not catch this.

The benchmark manifest also omits the existing [scene3d render benchmark](crates/gpui-scene3d/benches/render_bench.rs) and [transformation flow benchmark](crates/gpui-dataset-transformation/benches/flow_bench.rs). Add these, plus retained camera/field updates, volume, import, resize and export working-set cases.

### What the current tests establish well

The [CI workflow](.github/workflows/ci.yml) contains desktop build/test jobs, platform compile checks, native UI smoke, visual/Metal work, API/dependency checks, coverage and a pretext Miri job. The codebase has actual allocation contracts, property tests, mesh pipeline integration tests and some CPU/GPU differential assertions. Examples include [builder allocation contracts](crates/gpui-builder/tests/allocation_contracts.rs), [pretext allocation contracts](crates/gpui-pretext/tests/allocation_contracts.rs), and the flow diagnostics comparison in [gpu.rs](crates/gpui-dataset-transformation/src/gpu.rs), lines 477–510.

These are useful assets. The problem is not an absence of testing infrastructure; it is that several important contracts are not asserted, and the performance evidence path can fail open.

### Where confidence is weaker than test names/counts suggest

- `gpu_render_matches_scene_and_updates_by_uniform_only` checks that the center differs from the background and orbit changes enough bytes. It does not compare the scene with the CPU renderer or exercise translated clipping. See [gpu_render.rs](crates/gpui-scene3d/src/gpu_render.rs), lines 594–628.
- GPU initialization errors can return early as a successful test. Some tests label all such errors “no adapter,” although a device/shader/configuration failure may be actionable. Dedicated GPU jobs must require the expected backend and report executed/skipped cases separately.
- Shader-string presence and uniform-size tests check plumbing, not clipping or compositing semantics.
- [text_input_corpus.rs](crates/gpui-pretext/tests/text_input_corpus.rs) uses a synthetic measure and checks basic layout properties. It is not an end-to-end native shaper, bidi-caret or IME composition test.
- Mobile compilation does not execute UIKit/JNI lifecycle, display scheduling, thermal reporting or memory pressure. Desktop tests of shared modules cannot substitute for those behaviors.
- Miri is focused on pretext. The platform-neutral raw-handle/registry ownership core deserves similar adversarial coverage.
- [qa_fuzz_check.sh](scripts/qa_fuzz_check.sh) can skip when fuzz tooling is absent and primarily checks a fuzz target builds. That is distinct from sustained corpus execution, sanitizers and regression corpus replay.
- Timing medians and a 20% threshold do not bound retained memory, allocation traffic, CPU wakeups or joules. Improve evidence quality before tightening thresholds.

## 8. Taffy evaluation

### Taffy is already in the rendering stack

[Cargo.lock](Cargo.lock) resolves Taffy 0.14.0. The locked GPUI fork's `TaffyLayoutEngine` owns a `TaffyTree`, creates nodes for requested layout, supplies measurement callbacks, and clears the tree/maps between draws. The fork's window draw path calls `layout_engine.clear()` after drawing. These were checked in the local locked dependency source: [Taffy adapter](https://github.com/pierreaubert/sotf-3rdparties/blob/d476ae9bc3165145d4a8e43b6bafbef11b196a04/gpui/crates/gpui/src/taffy.rs), especially lines 35–83 and 180–224; [window draw path](https://github.com/pierreaubert/sotf-3rdparties/blob/d476ae9bc3165145d4a8e43b6bafbef11b196a04/gpui/crates/gpui/src/window.rs), around line 2899.

Consequently, “adopt Taffy” is not a new-engine optimization. The useful question is **how much layout/tree/measurement work survives between frames, and whether invalidation can be narrower**. GPUI also has cached-view reuse; this is not a claim that every element in every view is fully rebuilt on every paint.

Taffy supplies flex, grid and block layout, with a high-level tree and lower-level integration APIs. Its published benchmark table measures layout computation and excludes tree creation; it also does not supply application text shaping. Those numbers cannot predict this toolkit's end-to-end savings. [Primary source: Taffy](https://github.com/dioxusLabs/taffy), [TaffyTree API](https://docs.rs/taffy/latest/taffy/tree/struct.TaffyTree.html).

### Recommended use

1. **Instrument the current adapter first.** Count nodes created, layout invocations, dirty subtrees, text measurements, style conversion, retained capacities and time in each stage. Separate cold construction, unchanged redraw, one-node mutation and resize.
2. **Use existing retention before creating another tree.** `RetainedLayoutSolver` already preserves solved storage and the measurement cache in [solve.rs](crates/gpui-builder/src/solver/solve.rs), lines 135–188. Verify callers reuse it instead of invoking allocating convenience paths repeatedly.
3. **Keep builder policy distinct from CSS geometry.** Priority collapse, display tiers and auto-axis policy are application constraints. Use that policy to select/parameterize the ordinary GPUI layout, then let the existing Taffy path compute geometry. Replacing policy with flex/grid alone would lose behavior. Avoid calculating the same geometry independently in builder and a second Taffy tree.
4. **Prototype retained Taffy nodes in the GPUI fork.** Stable identities, explicit style/children/measure generations and ancestor dirty propagation can preserve layout caches across frames. Removed/reparented nodes must be reclaimed; cache hits must remain correct for text, DPI, locale, visibility and available-space changes. The current clearing behavior makes this a fork-level lifecycle change, not a local crate substitution.
5. **Consider the lower-level adapter only if profiling warrants it.** Exposing existing retained nodes through Taffy's layout traits may avoid a duplicate tree, but the implementation and invalidation complexity must earn its cost. Keep one compatible Taffy version and one owner for pixel rounding.

### Experiment and decision gate

Compare current GPUI, existing retained builder usage, and a retained-Taffy prototype on 100/1,000/10,000-node trees; real forms; long Unicode text; virtualized tables; nested split panes; and continuous resize. Include topology changes, one-label changes, DPI/font changes and removal/reparenting. Measure total frame CPU time, allocations, peak/steady memory and real-device energy, with layout outputs and interaction hit regions checked for correctness.

A reasonable **proposed** adoption threshold is at least 20% lower layout-stage CPU on representative mutation workloads, measurable end-to-end benefit, and no unacceptable steady-memory or correctness regression. This is a decision threshold, not a measured expected speedup. Fixing scene reconstruction or missing virtualization may save much more CPU than changing the layout engine's integration.

## 9. scene3d improvement plan, including CUDA and MLX

### 9.1 Target architecture

Preserve the existing separation: mesh owns canonical data, transformation owns numerical operations, scene3d owns rendering, and GPUI owns presentation/lifecycle. Introduce an internal backend-neutral resource contract with:

- Topology, geometry, field, material and camera revisions tracked separately.
- Validity masks, units/precision policy, element association and field provenance carried with results.
- Device identity, owned-buffer lifetime, completion fence/event and byte accounting.
- Explicit capabilities and fallbacks; CPU-readable results requested separately from GPU-resident results.
- Bounded asynchronous work, cancellation/generation checks and a small maximum number of in-flight frames.

Intended interactive data flow:

```text
shared canonical dataset
  -> retained topology / spatial index / derived geometry
  -> resident field calculation (CPU, WGSL, optional CUDA or MLX)
  -> resident scalar / normal / index buffers
  -> scene3d draw encoded with the host renderer
  -> presentation

CPU readback only when requested: export, analysis result, bounded picking data
```

Do not make one enormous backend trait own layout, parsing, numerical transforms and presentation. Keep a narrow compute-resource boundary and a separate renderer interface.

### 9.2 Phase A: correctness and observability

Implement C1–C5 first, including prepared-field consistency. Add counters for preparation, uploads, readback bytes, wait time, cache bytes and in-flight memory. Define a numerical test corpus with analytic fields, thin/degenerate tetrahedra, large origins, mixed scales and invalid samples. Keep a small trustworthy f64 CPU reference.

Agree on normal orientation, scalar interpolation, clipping limits, alpha/compositing and missing-data behavior. Correctness fixes must precede backend speed comparisons; otherwise a faster backend may simply be doing less or different work.

Deliverable: failing regressions converted to passing tests and an honest benchmark gate. No CUDA/MLX dependency required.

### 9.3 Phase B: retain and integrate the renderer

Extend the existing `GpuRenderer`/`GpuScene` rather than rebuilding their retained upload design:

- Add construction from the host device/queue and capability policy.
- Add encoding into a caller-owned target/pass or custom-draw integration; avoid compulsory standalone submit/readback.
- Provide appropriate target usages for the chosen compositing route; the current standalone target is designed around render-attachment/readback usage.
- Retain derived topology, spatial chunks, normals, material state and render targets. Invalidate by explicit revision.
- Add frustum culling, spatial chunk order and screen-error LOD for display. Preserve full-resolution canonical data for analysis/export.
- Bound uploads and rebuild work per frame; reuse staging. Resize should reuse/grow within limits and release obsolete large targets.
- Make `SceneElement` select this path when supported; retain a bounded CPU fallback with reusable scratch and correct DPI.

Deliverable: camera orbit with no geometry extraction/upload and no color-image CPU readback; field updates touch field data only. Measure end-to-end improvement and memory on desktop and mobile.

### 9.4 Phase C: improve portable CPU/WGSL computation

Build on `PreparedFlow`'s existing retained adjacency and GPU point reduction. Expose outputs as resident fields instead of mandating three CPU readbacks. Precompute fixed geometry where its memory cost is justified; compare per-tet-plus-gather against the current repeated per-point tetrahedron evaluation. Construct CSR with counts/prefix sums rather than per-point growable vectors when that reduces peak memory.

Fuse requested diagnostics and omit unrequested outputs. Partition dispatch and storage by device limits. Reuse pipelines, bind groups and buffers. For slice/threshold/isosurface, evaluate classify → prefix-scan → compact/emit pipelines with bounded output capacity and an explicit overflow/retry policy. Prefer chunk-local work to unbounded temporary arrays.

For volume rendering, introduce compact acceleration structures, empty-space skipping and a GPU raycasting path. Progressive quality should be cancellable and informed by interaction/thermal policy. Small datasets and sparse updates may remain cheaper on the CPU; select offload thresholds from total upload/compute/sync/render cost.

Deliverable: a strong portable baseline across supported Metal/Vulkan/D3D/WebGPU devices. This is the baseline against which CUDA and MLX must compete.

### 9.5 Phase D: optional CUDA backend

CUDA is most plausible for large repeated numerical work on NVIDIA systems: tetrahedral gradients, batched diagnostics, scan/compaction, large isosurfaces and volume kernels. It should implement the transformation/resident-resource boundary; keep the render/presentation interface independent.

Implementation plan:

1. Start with one operation, preferably repeated flow diagnostics on fixed topology, and compare against both CPU and retained WGSL. Include preparation and result handoff in timings.
2. Keep geometry, adjacency, fields and outputs resident. Use bounded pools and streams/events; evaluate CUDA Graphs only for a stable repeated workload after measuring launch overhead. Do not introduce a device-wide synchronization per frame.
3. Prototype graphics interoperability explicitly. CUDA supports importing graphics external memory and synchronization objects; Vulkan interop requires matching the physical device, commonly by UUID. This is a resource-lifetime/synchronization contract, not a cast from a wgpu buffer to a CUDA pointer. [NVIDIA graphics interoperability guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/graphics-interop.html).
4. Investigate a small audited native/hal bridge for the actual wgpu backend, using external-memory-capable allocation and semaphores/fences. If this is unavailable, provide a bounded asynchronous staging fallback and measure the copy cost. Vulkan and D3D integration require separate capability checks.
5. Retain f64 CPU/reference behavior for ill-conditioned cases; use f32/rebased coordinates only under declared error bounds. Consumer GPUs vary in double-precision throughput, so do not assume CUDA automatically makes f64 inexpensive.
6. Validate with numerical differential tests, allocation/limit tests and CUDA memory/race tooling. Test device mismatch, device loss, cancellation and resource destruction while work is pending.

**Go/no-go:** adopt only when end-to-end time and/or energy improves at the intended dataset sizes without exceeding the memory budget. Keep the feature optional and preserve the portable path on non-NVIDIA systems, mobile Apple devices and browsers. No CUDA speedup was measured in this audit.

### 9.6 Phase E: optional MLX/Metal backend

MLX is an array-computation candidate, not a replacement for the scene renderer. The most natural first experiment is vectorized field calculation or batched small-matrix diagnostics on Apple silicon. Irregular mesh traversal, variable-length emission and ray marching may be better expressed as custom Metal kernels or the existing WGSL path.

MLX's Apple-silicon memory model allows CPU/GPU operations on a common memory pool. That does **not** establish arbitrary wgpu/MLX buffer interoperability or eliminate synchronization and temporary storage. [MLX unified memory](https://ml-explore.github.io/mlx/build/html/usage/unified_memory.html).

Implementation plan:

1. Prototype the same operation and datasets as the portable baseline. Measure compilation/warmup separately from repeated execution, and include final result availability rather than timing only lazy graph construction.
2. Keep topology/constant arrays resident; compile stable shapes when appropriate. Bound graph lifetime and evaluate at explicit frame/task boundaries. Avoid building a growing lazy graph across a stream of frames. [MLX lazy evaluation](https://ml-explore.github.io/mlx/build/html/usage/lazy_evaluation.html).
3. Use a native C/C++ integration boundary or another validated native binding; do not add a Python runtime to mobile presentation. Pin MLX and its extension build together. MLX supports custom primitives/Metal kernels and manages command encoding internally; its C++ ABI is not stable across releases. [MLX custom extensions](https://ml-explore.github.io/mlx/build/html/dev/extensions.html).
4. Prove ownership and synchronization for any proposed shared `MTLBuffer`/texture path. If direct sharing is not supported by the chosen APIs, count the staging copy honestly. A shared physical memory pool does not imply zero-cost handoff between independent command queues.
5. Set explicit working-memory/cache limits and observe actual peak memory. Bound in-flight evaluations and trim on pressure/background transitions. Unified memory means computation and rendering compete within the same device budget. [MLX memory limit API](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_memory_limit.html).
6. Benchmark custom Metal or WGSL alongside MLX for irregular operations. Reject an elegant array formulation if broadcast/gather intermediates increase peak memory or energy. Check precision support against the numerical contract.
7. Start on macOS. Treat iOS availability, deployment target, binary size, API surface and physical-device memory behavior as a separate packaging/proof gate; do not infer mobile readiness from a Mac prototype.

**Go/no-go:** retain MLX only for workloads with measured benefit over the integrated Metal/WGSL path. A compute library that reduces kernel development time can still be unsuitable for the lowest-power interactive path. No MLX performance or mobile integration was measured here.

### 9.7 Shared acceptance matrix

| Workload | Measurements | Required invariants |
|---|---|---|
| Static scene/idle | CPU wakeups, callbacks, draws, retained bytes, energy over fixed duration | No repeated geometry work or unexplained frame pump |
| Camera orbit | CPU/frame, GPU/frame, p50/p95/p99 frame time, upload/readback bytes | Geometry stable; correct clipping and DPI |
| Streaming scalar/vector field | Preparation, conversion, upload, compute, handoff, total latency and joules/update | Coherent revisions; masks preserved; bounded backlog |
| Large surface/isosurface | Peak CPU/GPU memory, output size, chunk throughput | Budget-aware output; correct topology and limits |
| Volume | Quality/error, samples/ray, empty-space skip ratio, memory, energy | Declared step/opacity behavior and cancellation |
| Export | Peak memory, bytes/frame, total CPU/energy, cancellation latency | Bounded queue; no pipe deadlock; consistent fields |

Run CPU/WGSL/CUDA comparisons on NVIDIA hardware and CPU/Metal-WGSL/MLX comparisons on Apple hardware. Include at least one constrained phone/tablet for the portable path. Record backend/device identity and report unsupported paths explicitly.
