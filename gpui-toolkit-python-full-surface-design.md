# GPUI Toolkit Complete Python Surface Design

**Status:** Proposed design  
**Date:** 2026-08-06  
**Scope:** `gpui-toolkit --features all`  
**Builds on:** `gpui-toolkit-simulation-app-requirements.md`

## 1. Outcome

The `gpui_toolkit` Python package must let a Python application use every
consumer-facing capability of the `gpui-toolkit` aggregate crate without
writing Rust. The existing simulation requirements remain the first product
acceptance target; this document defines the larger API and the mechanical
parity contract needed to prevent the Python surface from becoming a small,
hand-maintained subset.

Python owns application state and callbacks. Rust owns GPUI, native platform
integration, rendering, accessibility, resource lifetimes, and APIs whose
objects cannot safely cross a process boundary. The Python API exposes those
Rust capabilities through typed declarations, value APIs, commands, events,
and opaque resource handles.

## 2. Normative meaning of 100% coverage

The coverage baseline is the set of consumer-facing capabilities exported by
the crates enabled by the aggregate `all` feature:

- `ui`: `gpui-builder`, `gpui-design`, `gpui-keybinding`, `gpui-pretext`,
  `gpui-ui-kit`, and the behavior generated by `gpui-ui-kit-macros`;
- `audio`: `gpui-audio-kit`;
- `charts`: `gpui-d3rs` and `gpui-px`;
- `themes`: `gpui-themes`;
- `tooling`: `gpui-component-lab`, `gpui-design-tools`, `gpui-miniapp`,
  `gpui-profiler`, `gpui-python-runtime`, and `gpui-scaffolder`;
- `platform`: `gpui-au` and `gpui-ios` where the target supports them;
- the aggregate crate's stability, QA, packaging, and release reports.

The inventory also scans every first-party `crates/gpui-*` package so an
aggregate-feature omission cannot make the report falsely reach 100%. At the
time of this design, `gpui-android` and `gpui-showcase` are not re-exported by
the aggregate `all` feature. `gpui-android` is nevertheless a consumer-facing
platform backend and belongs in the Python platform contract. Showcase-only
code may be classified `non-consumer`, while the capabilities demonstrated by
the showcase must resolve to their owning public crates. CI reports any other
first-party package outside the aggregate and requires an explicit decision.

Coverage is semantic, not ABI-shaped. A Rust capability is complete only when
one of these dispositions appears in the checked-in surface manifest:

1. `direct`: the Python API has the same value semantics;
2. `declarative`: Python emits a typed spec rendered or managed by Rust;
3. `command`: Python invokes a typed host operation and receives a typed result;
4. `event`: Rust state or interaction is observable as a typed Python event;
5. `opaque`: Python owns a stable handle while Rust owns the non-serializable
   resource;
6. `host-owned`: the capability is automatic and has observable configuration
   or state, such as focus or accessibility bridging;
7. `platform-unavailable`: the API exists but raises a typed unsupported error
   after capability negotiation on the current target;
8. `non-consumer`: build macros, test fixtures, showcase-only code, private
   implementation details, and raw GPUI/wgpu/OS handles, with a documented
   reason and reviewer approval.

`non-consumer` is not a general escape hatch. It may not be used for a public
widget, algorithm, design token, chart, interaction, tool, or platform service.
Procedural macros are covered by exposing their resulting behavior: component
builder properties, theme fields, and form-field metadata.

The release gate is 100% disposition coverage and 100% conformance coverage
for every entry whose disposition is not `non-consumer`. Platform-unavailable
entries must still have importable Python types, capability metadata, and
unsupported-path tests.

## 3. Architecture

### 3.1 Four layers

```text
Python application
    gpui_toolkit typed API and asyncio runtime
        versioned session protocol + resource transport
            Rust host adapters
                GPUI Toolkit crates / GPUI / wgpu / platform backends
```

The package has four kinds of API:

- immutable, JSON-safe value objects such as colors, axes, constraints, theme
  tokens, keybindings, and validation reports;
- retained declarations such as widgets, charts, workflow graphs, and scenes;
- session services such as windows, dialogs, clipboard, notifications, jobs,
  resources, profiling, and platform integration;
- pure algorithms backed by Rust RPC when keeping behavior identical matters,
  such as D3 layouts, text layout, layout solving, color transforms, and theme
  validation.

The public API must not expose arbitrary `dict[str, Any]` as its primary
contract. Escape hatches may accept mappings only behind an `experimental`
namespace and may not count toward parity.

### 3.2 Package layout

```text
gpui_toolkit/
  app.py                 # App, Window, lifecycle, commands, menus
  events.py              # typed event union and handler protocols
  state.py               # State, Binding, Computed, validation
  effects.py             # dialogs, clipboard, URLs, credentials, notifications
  jobs.py                # tasks, processes, cancellation, bounded logs
  resources.py           # arrays, images, meshes, mapped/shared resources
  ui/                    # complete gpui-ui-kit declarative surface
    forms.py navigation.py feedback.py data.py overlays.py layout.py
    workflow.py mobile.py accessibility.py animation.py i18n.py
  layout.py              # complete gpui-builder value/solver surface
  design.py              # gpui-design types, presets, tokens, reports
  themes.py              # gpui-themes models, gallery, editor declaration
  charts.py              # complete gpui-px surface
  d3/                    # complete gpui-d3rs algorithm and primitive surface
  audio.py               # complete gpui-audio-kit surface
  text.py                # gpui-pretext preparation and line layout
  keybindings.py         # registry, presets, conflicts, discovery
  lab.py                 # component-lab stories and visual manifests
  tooling.py             # design-token tools and scaffolding
  profiler.py            # allocation probes and budgets
  platform.py            # AU/iOS/Android capabilities and services
  reports.py             # aggregate stability/release/QA reports
  protocol/              # generated wire models; not normally imported
```

Top-level convenience exports may remain small. Every public object must have
one canonical module to avoid name collisions such as UI and theme `Color` or
audio and D3 `Scale`.

### 3.3 Generated surface registry

A checked-in `python-surface.toml` is the source of parity metadata. Each entry
contains:

```toml
[[capability]]
id = "gpui-ui-kit.input"
rust_path = "gpui_ui_kit::Input"
python_path = "gpui_toolkit.ui.TextInput"
disposition = "declarative"
protocol_types = ["text_input", "text_edit", "text_commit"]
platforms = ["macos", "linux", "windows", "ios"]
tests = ["python/tests/conformance/ui/test_text_input.py"]
```

A generator combines Rustdoc JSON, explicit module annotations, feature
metadata, and the manifest to produce:

- frozen Python dataclasses, enums, unions, and `.pyi` declarations;
- Rust protocol enums and capability descriptors;
- JSON Schema for wire validation;
- `gpui_toolkit.capabilities()` results;
- documentation and a Rust-to-Python coverage matrix.

CI fails when a public exported capability appears, disappears, or changes
shape without a manifest decision. CI also fails for duplicate IDs, missing
tests, unresolved Python paths, undocumented exclusions, or protocol types
that are not understood by both peers.

## 4. Common Python object model

### 4.1 Nodes and properties

Every retained object derives from a typed `Node` model and has:

- a stable, application-defined `id` unique within the window;
- an explicit node `kind` and schema version;
- typed properties with omission distinct from `None`;
- optional `visible`, `enabled`, responsive sizing, accessibility, tooltip,
  style token overrides, and test ID;
- typed children or slots rather than unconstrained child lists;
- declared event bindings.

Node models are immutable. Updates use state bindings or revisions, not mutation
of arbitrary dictionaries. `App.view()` may return a new tree and the Python
runtime reconciles it by stable ID, or code may submit an explicit transaction.

```python
class Studio(App):
    model = State[Path | None](None)
    running = State(False)

    def view(self) -> ui.Node:
        return ui.VStack(
            id="root",
            children=[
                ui.PathInput(id="model", value=self.model.bind(), mode="open_file"),
                ui.Button(id="run", label="Run", disabled=self.running.bind()),
            ],
        )

    @on.click("run")
    async def run(self, event: events.Click, cx: AppContext) -> None:
        async with cx.jobs.task("simulation") as job:
            await self.simulate(job)
```

### 4.2 Values, bindings, and validation

`State[T]`, `Binding[T]`, and `Computed[T]` provide typed application state.
Rust keeps draft widget state while an edit is in progress and sends preview,
change, commit, cancel, focus, blur, selection, and validation events as
appropriate. Python remains authoritative after commit.

Validation uses `ValidationResult` with severity, code, message, details, and
optional fix action. Form and collection validation can target a node or row.
Secret bindings are separate types and are always redacted in serialization,
traces, exceptions, snapshots, and `repr`.

### 4.3 Events and commands

Events are a closed, generated tagged union. All events include session,
window, node, sequence, timestamp, action, revision, modifiers, and
correlation IDs. Specialized payloads cover pointer, keyboard, focus, edit,
commit, selection, sort, resize, drag, drop, scroll, viewport, chart, workflow,
3D picking, menu, dialog, window, and accessibility actions.

Handlers may be synchronous or asynchronous but never run on the render
thread. The runtime supports coalescing previews, superseding stale handlers,
debounce/throttle policies, acknowledgement, rejection, and cancellation.

Commands and menus use registered IDs and typed payload/result models. No
Python-provided string is evaluated as Rust, Python, or a shell command.

### 4.4 Effects and host services

`AppContext` provides typed async services:

- open/save/directory dialogs and drag/drop paths;
- confirmation, prompt, alert, toast, and system notification;
- clipboard text, images, and typed application data;
- URL opening and reveal-in-file-manager;
- credential store by opaque reference;
- windows, menus, focus, accessibility announcements, and application quit;
- safe child processes with argument vectors and explicit environment policy;
- app data/cache/log directories and atomic state persistence;
- theme, locale, display, reduced-motion, and platform capability observation.

Every consent-bearing effect is correlated with a requesting event and returns
a typed success, cancellation, unsupported, denied, or failed result.

### 4.5 Resources

Large or retained data never has to be encoded as JSON decimal arrays.
`Resource[T]` supports immutable and replaceable buffers for numeric arrays,
images, fonts, table pages, chart series, audio meter frames, and 3D geometry.
Transport negotiation selects inline JSON, compact binary frames, memory maps,
or shared memory. Resource updates carry shape, dtype, byte order, null/finite
policy, generation, checksum, and size.

Rust enforces per-kind and total budgets, reference counts, LRU eviction, and
generation checks. A stale handle produces a structured error. NumPy is an
optional zero-copy adapter, not a required dependency.

## 5. Complete UI surface

The Python declarations must cover all public `gpui-ui-kit` component families
and their builder properties, variants, sizes, themes, keyboard behavior,
focus behavior, accessibility metadata, slots, and callbacks.

| Family | Required Python components and behavior |
|---|---|
| Core | `Button`, `ButtonSet`, `IconButton`, `Card`, `AdaptiveOverflow` |
| Overlays | `Dialog`, `ConfirmDialog`, `ContextMenu`, `Menu`, `MenuBar`, `Popover`, `Toast`, focus trapping and normalized overlay keys |
| Forms | `TextInput`, password input, `NumberInput`, `Select`, `Checkbox`, `Toggle`, `Slider`, `ColorPicker`, form rows, help, units, validation, draft and commit semantics |
| Navigation | `Tabs`, `Accordion`, `Breadcrumbs`, `Wizard`, sidebar, command palette, tree view |
| Data display | avatar/group/status, badge/dot, image, shortcut label, progress/circular progress, QR/animated QR, spinner/loading dots, step indicator, table, heading/text/code/link |
| Feedback | alert/inline alert, search bar, tooltip, loading overlay, notification, empty state |
| Layout | horizontal/vertical stacks, divider, spacer, settings form, pane divider, split pane, swipe panel, status bar, toolbar, responsive overflow |
| Collections | tag, drag list, keyed collection patches, selection, sorting, pagination and virtual windows |
| Workflow | canvas, graph, nodes, ports, connections, selection, hit testing, viewport, drag/connect interactions, context menus, undo/redo commands and history |
| Mobile | dynamic type, safe-area insets, momentum scrolling, pull-to-refresh, swipe actions, waveform scrubbing and context preview |
| Infrastructure | animation/keyframes/springs/easing, i18n/translations, focus groups, ARIA models, native accessibility bridge, color tokens, theme and design-system access |

The table component supports typed columns and cells, stable row IDs, async or
resource-backed data sources, virtualization, selection, sort, resize, pin,
pagination, edit, row actions, keyboard navigation, and incremental keyed
patches. A log view is a specialized virtual table with bounded retention,
follow-tail, pause, severity filters, copy, clear, and export.

Workflow models use the same command/history semantics as the Rust component.
Python callbacks receive semantic graph operations; pointer-rate drag updates
remain local to Rust unless explicitly subscribed.

## 6. Layout, design, themes, text, and keybindings

### 6.1 `gpui-builder`

Python exposes `Axis`, `Sizing`, `DisplayTier`, slot/container nodes, layout
preferences, ratio and collapse state, plugin chassis specs, accessibility
metadata, snapshots, validation, inspection, and solved-tree results. `solve`,
retained solve, matrix solve, text-measured solve, and debug reports execute in
Rust to preserve exact behavior. Python-defined layouts may bind the solved
result directly to UI slots without a protocol round trip on every resize.

### 6.2 `gpui-design`

All design languages, platforms, systems, spacing, corner, typography,
elevation, interaction, animation, audio-control, and layout-threshold rules
are typed value models. Python can select presets, inspect and override tokens,
export Style Dictionary data, and request conformance/documentation/release
reports. Invalid finite or range values produce the same findings as Rust.

### 6.3 `gpui-themes`

Python covers editor, graph, meter, spectrum, EQ, plugin, accessibility, accent,
and terminal palettes; appearances and modes; built-in/community themes;
gallery entries; schedules; transitions; and color editing. The host owns live
theme application and animated transitions. Community bundle import is
validated in Rust before activation.

### 6.4 `gpui-pretext`

Python exposes engine/prepare profiles, whitespace and line-break strategies,
text budgets, prepared text, line cursors/ranges/results, rich spans, variable
font axes, inline Markdown parsing, bidi/accessibility runs, and language
support reports. Text measurement implementations may be host-native or a
batched Python protocol, but UI layout always uses the host-native path.

### 6.5 `gpui-keybinding`

Python exposes keymap presets, categories, documented bindings, registries,
navigation mappings, platform labels, conflicts, command-palette entries,
hints, and search. Python providers return serializable declarations rather
than Rust trait objects. The host registers bindings and emits command IDs.

## 7. Charts and D3

### 7.1 `gpui-px`

The high-level API includes scatter, line, bar, area, box plot, heatmap,
contour, isoline, pie, donut, treemap, surface 3D, and all supported builder
properties. It includes multi-series data, colors and scales, curve and dash
types, annotations, axes, legends, size, themes, accessibility summaries,
interaction state, and SVG/PNG/CSV export.

Chart state has stable chart, axis, legend, annotation, and series IDs.
Geometry/data, style, annotations, selection, and viewport are independently
patchable. Zoom, pan, brush, nearest-point inspection, legend toggling, and
reset run locally in Rust; subscriptions emit throttled semantic events.

### 7.2 `gpui-d3rs`

The `gpui_toolkit.d3` namespace covers every public D3 module:

- array/statistics/binning/search, random, time, timer, format, and fetch
  parsing;
- color and color schemes, numeric/color/string/transform/zoom interpolation,
  easing, dispatch, transition, and selection/data joins;
- linear, log, power, symlog, quantize, quantile, threshold, ordinal, band,
  point, time, and sequential/diverging scale capabilities present in Rust;
- axes, grids, legends, text layout, shapes, curves, stacks, pies/arcs, symbols,
  contours, density, hexbin, Delaunay, Voronoi, polygons, quadtrees, and LOD;
- hierarchy, treemap/partition/pack/tree/cluster, force, chord, sankey, geo,
  tiles, brush, drag, and zoom;
- GPUI surface primitives and feature-gated GPU 2D/3D primitives through
  declarative specs and opaque resources.

Pure value algorithms are batch RPCs backed by Rust so edge cases stay
identical. Renderer and interaction objects are retained host objects. Fetch
requires an explicit network capability and follows host sandbox policy.

## 8. Audio surface

Python exposes potentiometer, vertical slider, volume knob, horizontal and
level meters, spectrum, frequency/dB axes, tick rows, audio scales, interaction
configuration, value tracking, accessibility summaries, automation patterns,
design tokens, themes, and visual-regression manifests.

Pointer-rate drag, scroll, keyboard, and meter rendering remain in Rust.
Python receives preview/commit events at declared rates. `MeterStream` and
`SpectrumStream` use bounded resources or binary frames, never unbounded JSON
messages. The API declares channel count, sample/rate metadata, ballistics,
finite-value policy, and drop/coalesce behavior.

## 9. Tooling and platform surface

### 9.1 Tooling

- Component lab: story documents, props, registries, renderers, presets,
  responsive preview matrices, validation, conformance and visual manifests.
- Design tools: token import/export/validation and handoff reports.
- Mini app: Python `App` and `WindowConfig` cover shell title, dimensions,
  menu, theme/language switching, and builder-backed content layout.
- Profiler: allocation snapshots, probes, budgets, named samples, and host
  telemetry subscriptions. Unsupported allocator modes report zeros with the
  same capability metadata as Rust.
- Scaffolder: typed project options, dry run, generated-file preview, and
  scaffold results. Writes require explicit target paths and collision policy.
- Aggregate reports: crate stability, dependency hygiene, publish plan,
  release notes/artifacts, packaging, QA, platform capability, and vendored
  patch reports are available as typed read-only values.

### 9.2 Platform

AU, iOS, and Android APIs are represented in `gpui_toolkit.platform` with
importable, platform-neutral types. On supported targets the host exposes
embedding and view lifecycle, scale/display/safe-area/keyboard state, touch
and text input, accessibility, clipboard/file/URL services, frame requests,
momentum/platform-view integration, and declared platform capabilities. Native
pointer, Metal/wgpu, Objective-C/Swift/JNI, and raw window/view handles remain
host-owned.

Python applications do not initialize an AU view controller or mobile render
surface directly. Packaging metadata selects the adapter and the host sends
typed lifecycle events. An unavailable adapter raises `UnsupportedCapability`,
not `ImportError`, so application code can declare fallbacks.

## 10. Session protocol

The simulation session protocol becomes a framed, versioned protocol with five
independently negotiated schemas:

- app and node declarations;
- events, commands, effects, and lifecycle;
- patches and state reconciliation;
- resources and binary frames;
- capability manifest and diagnostics.

Each peer advertises min/max versions, feature flags, platform qualifiers,
limits, and content encodings. Required capabilities are declared before the
first snapshot. Initialization fails with a complete compatibility report,
not at the first unsupported node.

All messages include session ID, monotonically increasing sequence, protocol
version, correlation ID where applicable, and byte length. Transactions use a
base revision and atomic operation list. The host rejects stale revisions,
unknown nodes/resources, invalid types, cycles, duplicate IDs, oversized
messages, and unsupported capabilities before mutation.

The Python process has one long-lived asyncio loop. Stdio control frames and
stderr are drained concurrently. Binary data uses a separate negotiated
channel. Heartbeat, graceful shutdown, crash recovery, restart, handler
cancellation, and late-result suppression are host/runtime responsibilities.

## 11. Compatibility and distribution

The workspace version is the only version source. Rust crate metadata, Python
package metadata, bundled host metadata, protocol generators, and runtime
reports consume it. A wheel contains the Python code and a compatible host for
its platform, or depends on an application bundle that declares the matching
host. Production never discovers a repository or invokes Cargo.

Python supports the versions declared in package metadata. The public API uses
deprecation warnings for at least one minor release before removal. Wire fields
are additive within a schema version; semantic changes require a new version
and generated migration or explicit compatibility adapter.

Optional features affect negotiated runtime availability, not whether public
Python names can be imported. `require_capabilities(...)` gives an early,
actionable error. API documentation marks platform and host feature support.

## 12. Verification and parity gates

### 12.1 Generated checks

CI must run:

1. Rustdoc export inventory versus `python-surface.toml`;
2. generated Rust/Python/schema files are clean;
3. Python import and `.pyi` resolution for every manifest path;
4. serializer round trips for every value, node, event, command, effect,
   report, and error variant;
5. bidirectional unknown-version and unknown-field policy tests;
6. a coverage report that is exactly 100%, with exclusions printed verbatim.

### 12.2 Behavioral conformance

Every manifest entry points to at least one conformance test. Tests compare
Python-observed behavior to the Rust API or a shared golden fixture, including
invalid inputs. Component tests cover properties, events, keyboard, focus,
accessibility, narrow layout, disabled/read-only state, and theme variants.

Algorithm tests use shared property/golden vectors. Visual components use the
existing visual manifests across declared viewports and color schemes. Charts,
workflow, tables, logs, audio streams, and 3D resources have retained-state and
incremental-update tests. Platform-unavailable entries test typed failures.

### 12.3 End-to-end applications

The suite includes:

- the Speaker Studio acceptance application from the simulation requirements;
- a complete component gallery generated from the UI manifest;
- a D3/PX chart and interaction gallery;
- an audio control/meter application with synthetic bounded streams;
- a workflow editor with undo/redo and persistence;
- theme editor and component-lab applications;
- desktop clean-install smoke tests and supported AU/mobile adapter tests.

Performance gates cover render-thread non-blocking behavior, event latency,
10,000-row virtualization, high-rate meters, large chart/mesh resources,
resource eviction, and bounded process/log memory.

## 13. Delivery plan

1. **Inventory and generation:** add `python-surface.toml`, Rustdoc inventory,
   code generation, coverage reports, common value types, and parity CI.
2. **Runtime foundation:** finish persistent asyncio sessions, reconciliation,
   typed events/effects, resources, supervision, compatibility, and packaging.
3. **Complete UI:** generate and adapt all UI-kit nodes, interaction models,
   workflow, accessibility, animation, i18n, and mobile declarations.
4. **System APIs:** expose builder, design, themes, pretext, and keybindings,
   including pure Rust-backed batch calls and reports.
5. **Visualization and audio:** complete gpui-px, D3 algorithms/primitives,
   retained 3D, audio controls, and streaming resources.
6. **Tooling and platform:** component lab, design tools, profiler, scaffolder,
   aggregate reports, AU, iOS, and Android lifecycle adapters.
7. **Closure:** eliminate every unclassified manifest item, run cross-platform
   conformance and clean-install applications, publish the 100% report.

Each phase must update the manifest and may not reduce the coverage percentage.
New Rust public capabilities require a Python disposition and test in the same
change once the parity gate is enabled.

## 14. Definition of done

The Python surface is feature complete only when:

- the parity report shows every `gpui-toolkit --features all` consumer
  capability classified and every non-excluded capability conformant;
- all public Python APIs are typed, documented, versioned, and importable on
  every supported platform;
- unsupported target-specific behavior fails through capability negotiation;
- all UI components and visualization/audio primitives render and interact
  through Python declarations without custom Rust application code;
- all pure algorithm, design, layout, text, keybinding, tooling, and report
  capabilities have Python value or command APIs;
- retained state survives unrelated patches and large resources use bounded,
  observable storage;
- accessibility and keyboard conformance applies to the complete interactive
  surface;
- the Speaker Studio scenarios and the generated full-surface galleries pass;
- an installed application launches without Cargo or a source checkout;
- no raw GPUI, wgpu, Metal, Objective-C, Swift, or OS handle crosses into
  Python, and every such host-owned capability has an observable semantic API.
