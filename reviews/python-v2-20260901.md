# Python Wrapper v2: Complete Toolkit and Large-Data Bindings

**Status:** Proposed architecture and delivery plan

**Date:** 2026-09-01

**Scope:** `gpui-toolkit` Python package, native extension, protocol, and installed host

**Compatibility:** Clean package-level break from Python v1

## Goals and critical assessment

Python v1 is not a trustworthy binding:

- Python accepts arbitrary `**props`, while Rust silently ignores unsupported fields.
- Python declarations, Rust IR, host rendering, capabilities, and documentation drift independently.
- The installed host reuses a large showcase renderer and frequently approximates components instead of using native toolkit implementations.
- Tables serialize rows into the UI document, and charts generally serialize vectors inline. This cannot scale to millions of rows or frequently updated data.
- The protocol rebuilds too much state and does not preserve component, dataset, scroll, focus, or GPU-resource identity.
- Existing capability declarations are too coarse to prove component, parameter, event, slot, or library parity.

Version 2 will be a clean package-level break and provide:

- Immutable fluent builders for every configurable Python-facing API.
- Every semantic parameter, event, and slot from the stable public APIs.
- First-class live datasets and dense array resources for tables, charts, scenes, meshes, and audio visualization.
- Full stable API support in dependency order: `gpui-d3rs`, `gpui-px`, then `gpui-builder`, `gpui-pretext`, `gpui-ui-kit`, `gpui-audio-kit`, design/themes, profiler, and other bindable toolkit libraries.
- A hybrid wheel: native PyO3 bindings for computations and zero-copy Python buffers, plus the existing GPUI host for windows and rendering. No showcase-specific runtime or separate data service will be introduced.

Platform backends, procedural macros, showcase binaries, and GPUI execution-context objects are not Python libraries. They will be classified explicitly rather than counted as missing bindings.

## Binding architecture and public API

### Generated, audited bindings

- Introduce a parity registry with one entry for every stable public symbol, constructor parameter, builder method, event, slot, feature gate, and return type.
- Classify each entry as:
  - direct Python binding;
  - translated binding;
  - host-owned runtime operation;
  - intentionally excluded with a reviewed rationale.
- Use typed Rust v2 configuration structs as the canonical UI wire definition. Generate strict Python builders, enums, JSON Schema, capability manifests, fixtures, type stubs, and documentation from them.
- Generate the initial public-symbol inventory from rustdoc JSON. Require manual mapping metadata where Rust generics, traits, closures, or lifetimes prevent automatic binding.
- Reject unclassified additions in CI. “Full support” is achieved only when the registry contains no missing or partially consumed stable APIs.
- Use Python modules aligned with the Rust libraries:
  - `gpui_toolkit.data`
  - `gpui_toolkit.d3rs`
  - `gpui_toolkit.px`
  - `gpui_toolkit.builder`
  - `gpui_toolkit.pretext`
  - `gpui_toolkit.ui`
  - `gpui_toolkit.audio`
  - `gpui_toolkit.design`, `themes`, and `profiler`
- Preserve convenient v1 function names only as source-level shims that create v2 objects. They must not emit v1 IR or accept arbitrary properties.

### Hybrid native and host ownership

- Add an `abi3-py310` PyO3 extension to the wheel for Python 3.10–3.13.
- Execute pure and synchronous d3rs, layout-solver, pretext, formatting, geometry, hierarchy, scale, interpolation, and analysis APIs in the Python process.
- Release the GIL for substantial native computations. Python callbacks may be reacquired only on ordinary Python threads, never render, GPU, or realtime audio threads.
- Keep windows, GPUI entities, focus handles, render elements, GPU state, scroll handles, and realtime audio state in the host.
- Represent host-owned objects with typed, session-scoped handles supporting deterministic `close()` and context-manager cleanup.
- Map Rust concepts consistently:
  - scalars, enums, tokens, structures, and numeric results become typed Python values;
  - Rust traits become Python protocols or concrete strategy enums;
  - closures used by pure algorithms accept Python callables where thread-safe;
  - UI callbacks become named actions and typed events;
  - `AnyElement` factories become typed child or slot builders;
  - async native operations become Python awaitables;
  - feature-gated APIs remain importable but raise a typed capability error when unavailable.

### Immutable builder model

Every fluent setter returns a new object. Private storage and wire aliases allow method names to match the native API:

```python
from gpui_toolkit import data, px, ui

events = data.Dataset.from_pandas(frame, key="event_id")

table = (
    ui.Table("events")
    .data(events)
    .column(ui.Column("time").field("timestamp").sortable(True))
    .column(ui.Column("level").field("level"))
    .column(ui.Column("message").field("message").min_width(320))
    .selection_mode(ui.SelectionMode.MULTIPLE)
    .virtualize(row_height=28, overscan=12)
    .on_selection_change("events-selected")
)

chart = (
    px.scatter()
    .data(events.view().filter(data.col("enabled")))
    .x("frequency")
    .y("spl")
    .color("channel")
    .title("Frequency response")
    .lod(px.Lod.AUTO)
)
```

Builders use a private `UNSET` sentinel and omit unset values, allowing native defaults to remain authoritative. Explicit `None` is serialized only for nullable parameters.

## Large-data model

### Dataset and array resources

- Introduce `Dataset` for columnar/tabular data and `ArrayData` for dense numeric grids, tensors, images, spectra, and mesh buffers.
- Accept data through standard protocols without requiring Pandas or PyArrow:
  - Arrow C Data and C Stream;
  - Python dataframe interchange;
  - NumPy and Python buffer protocols;
  - DLPack for supported in-process native computations;
  - typed Python sequences as a small-data convenience.
- Provide optional adapters for Pandas, Polars, PyArrow, and NumPy when installed. Do not make those packages mandatory wheel dependencies.
- Convert small iterable inputs into the same resource model; tables and graphs must not have a separate inline-row execution path.
- Make builders immutable while dataset resources remain explicitly mutable and revisioned. Binding a dataset stores a stable resource ID, not a copy of its contents.

Public mutation operations will be:

```python
dataset.append(batch)
dataset.upsert(batch, key="event_id")
dataset.delete(keys)
dataset.replace(snapshot)
dataset.transaction()
dataset.close()
```

- Append works without a key. Stable selection, update, upsert, and delete require a declared primary key.
- Every commit increments a generation and emits schema-preserving deltas. Schema changes require an explicit replacement or migration operation.
- Support nulls, categorical/dictionary columns, temporal types, nested values where consumers support them, and explicit conversion errors otherwise.

### Views and data binding

- Add immutable `DatasetView` declarations for projection, typed filtering, sorting, grouping, aggregation, binning, windowing, and range selection.
- Use a serializable expression AST; never evaluate Python source strings in the host.
- Execute supported operations with native columnar kernels close to the consumer. A custom Python provider is an explicit fallback, not the default large-data path.
- Add reusable `DataBinding` objects that map columns to semantic roles such as `x`, `y`, `color`, `size`, `label`, `series`, row ID, tooltip, and accessibility description.
- Tables bind columns using field names or declarative cell templates. Custom cells use typed nodes with `FieldRef` expressions rather than one cross-process Python callback per row.
- Charts bind tabular datasets or dense `ArrayData`, depending on chart shape. Heatmaps, contours, surfaces, mesh plots, spectra, and scenes must not flatten dense arrays into JSON lists.
- Multiple components may bind the same dataset or view and receive the same committed generation atomically.

### Transport, virtualization, and lifetime

- Keep UI and control messages small. Dataset values must never be embedded in JSON session messages.
- Transfer local-process data through authenticated, session-scoped shared-memory or memory-mapped Arrow IPC batches. Use a binary chunked channel only where shared memory is unavailable.
- Track resource ID, schema fingerprint, generation, batch sequence, byte length, checksum, lease count, and acknowledgement.
- Use restrictive permissions, bounds validation, configurable memory limits, backpressure, deterministic release, and crash cleanup for shared resources.
- Guarantee zero-copy ingestion into in-process native algorithms when the source protocol permits it. Cross-process publication may copy once into shared storage; the host then reads that storage without another CPU copy. GPU upload remains an explicit necessary transfer.
- Dataset commits notify bound components independently of UI-tree patches.
- Table and tree consumers request only their visible window plus overscan. Sorting, filtering, and selection operate on stable row keys rather than materialized UI rows.
- Graph consumers use d3rs LOD, downsampling, spatial indexing, and incremental GPU-buffer updates. Appends and localized updates must not rebuild an unchanged full series.
- Retain scroll positions, focus, selections, dataset views, chart interaction state, GPU resources, and caches by stable builder key and resource generation.

## Complete library coverage and delivery order

### 1. Foundation

- Create the tracking issue.
- Freeze the stable public API inventory.
- Implement v2 schema generation, the PyO3 extension, capability negotiation, typed errors, resource handles, datasets, arrays, and shared-memory transport.

### 2. `gpui-d3rs`

- Bind every stable public computation module, including arrays, scales, colors, formatting, interpolation, time, hierarchy, contours, density, geometry, geographic operations, force, shape, LOD, and related result types.
- Bind rendered axis, grid, brush, drag, zoom, GPU, vello, and scene APIs through host-owned handles and declarative builders.
- Preserve feature and platform distinctions in the capability manifest.

### 3. `gpui-px`

- Bind every chart builder, parameter, annotation, legend, interaction, accessibility, export, and result type.
- Make dataset or array binding the primary input model for scatter, line, area, bar, boxplot, pie, heatmap, contour, isoline, treemap, surface, and mesh plots.
- Support live updates, multiple series, LOD policy, selection linking, viewport queries, and static export.

### 4. UI and application surface

- Extract the generic installed host from the showcase.
- Replace hand-rendered approximations with actual native components.
- Bind the complete `gpui-ui-kit` surface, including currently omitted component families and all layout, overflow, accessibility, theme, slot, state, and event parameters.
- Rewrite the Python showcase entirely against the installed public API. Native `Sidebar` scrolling and native step components are mandatory.

### 5. Remaining libraries

- Bind all stable `gpui-builder` solver inputs, priorities, constraints, solved layouts, snapshots, validation, and inspector outputs.
- Bind all stable `gpui-pretext` measurement, bidi, segmentation, line-breaking, rich-text, language, and layout APIs with buffer-friendly batch operations.
- Bind all stable `gpui-audio-kit` controls, meters, spectra, design tokens, state, and events. Python must never run in realtime audio callbacks.
- Complete design, themes, profiler, miniapp, accessibility, keybinding, state, resource, and other bindable toolkit modules using the same parity rules.
- Explicitly exclude backend crates such as AU/iOS/web platform implementations, proc-macro crates, examples, and showcase applications from runtime binding coverage.

Alpha wheels may be produced after each milestone, but stable 2.0 is released only after the complete registry for all targeted libraries is closed. V1 protocol support is removed in 2.0; a migration guide maps old constructors and properties to v2 builders.

## Verification and release gates

- Every mapped parameter has a non-default fixture proving Python acceptance, serialization or native-call conversion, Rust acceptance, adapter consumption, and result preservation.
- Unknown properties, node kinds, columns, incompatible dtypes, stale resource generations, and unavailable capabilities fail with typed, path-qualified errors.
- Builder tests cover immutability, chaining, slots, events, enum validation, omission versus `None`, dataset binding, stable keys, and generated type hints.
- Dataset tests cover Arrow, dataframe interchange, NumPy/buffer inputs, nulls, dictionary columns, schema changes, transactions, append/upsert/delete, backpressure, cancellation, crash cleanup, and concurrent readers.
- Large-table acceptance uses at least one million rows and proves that only the visible window plus overscan becomes UI elements.
- Large-chart acceptance uses multi-million-point data and proves LOD operation, bounded render work, incremental append, and preservation of interaction state.
- Control-channel tests prove large values never fall back to JSON and a small delta never retransmits an unchanged dataset.
- Cross-process tests verify leases, checksums, size validation, permissions, cleanup, and one-copy publication behavior.
- Native binding tests compare Python d3rs, px, builder, and pretext outputs against Rust fixtures, including property-based tests for numeric algorithms.
- Wheel tests install into clean Python 3.10–3.13 environments, compare the Python/native/host manifest digests, and exercise optional NumPy, Pandas, Polars, and PyArrow adapters.
- The installed Python showcase must match the native showcase’s sections, controls, scrolling, interactions, and representative visual snapshots.
- Stable 2.0 requires:
  - no unclassified stable public APIs in targeted libraries;
  - no silently ignored Python arguments;
  - no inline large-data protocol path;
  - no showcase-only rendering logic in the production host;
  - passing schema freshness, native parity, wheel, large-data, interaction, and visual gates.
